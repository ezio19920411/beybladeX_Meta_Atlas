# Beyblade X 搶購助手 — Product Specification

> 文件版本：v0.4.1  
> 整理日期：2026-11-04（Asia/Taipei）  
> 第一階段範圍：誠品線上購物 + Google Sheet 68 筆主名單 + UXUX11 10 筆補充據點（預設台中市）  
> 未來擴充：可切換台灣其他縣市，不改寫核心程式

## 1. 專案目標

建立一個手機優先、可加入手機主畫面的 Beyblade X 搶購助手，集中整理：

1. 誠品線上購物的指定陀螺商品、價格、購買入口及可觀察到的販售狀態。
2. 台中各 Funbox 門市的地址、官方 LINE 好友入口、Facebook 公告入口，以及最新販售／抽選活動。
3. 讓使用者可依縣市、門市、商品型號篩選，並以「逐項處理」方式開啟官方抽選頁或購買頁。
4. 記錄新公告、商品狀態變更及使用者已處理的項目，降低漏看或重複操作。

本工具是**資訊整合與操作輔助網站**，不是 Funbox 或誠品的官方系統，也不代替使用者登入、抽選、結帳或付款。

## 2. 範圍與優先順序

### 2.1 MVP 必做

- 預設地區：台中市。
- 地區選擇器：目前合併資料涵蓋 17 個縣市／縣，預設選取台中市；新增地區時只需增加資料，不需要改寫搜尋功能。
- Funbox 門市清單：以使用者 Google Sheet 的 68 筆資料為主要來源，另合併 UXUX11 公開 LINE 名錄的 10 個額外地點；其中 9 個提供額外 LINE ID，台東家樂福與台東秀泰共用同一個 LINE ID。補充據點獨立存放，不覆蓋 Google Sheet 資料。Facebook 粉專網址只對使用者主名單有值的門市提供；補充據點若無來源網址則留空。所有社群連結待逐店測試。
- 抽選／販售活動清單：商品型號、中文品名、門市、活動方式、開始與截止時間、原始公告、原始抽選網址、狀態及最後核對時間。
- 誠品商品追蹤：商品型號、商品名稱、價格、商品網址、頁面可見的購物操作／庫存訊息、最後檢查時間。
- 篩選：縣市、門市、商品型號／關鍵字、活動狀態、通路。
- 手動處理狀態：未處理、已開啟、已由使用者確認完成、已放棄。
- 行動版介面、外部連結、分享篩選網址。
- 清楚標示「資料最後更新」與單筆資訊的「最後驗證時間」。

### 2.2 第二階段

- 定時檢查誠品公開商品頁，偵測價格或頁面販售訊息變化。
- 監控公開可讀的門市 Facebook 公告；不能穩定讀取的來源提供貼上網址／手動匯入功能。
- 新抽選／販售公告提醒。
- PWA 安裝與瀏覽器通知。
- 抽選佇列（Agent-like workflow）：依序開啟活動頁，返回後提示下一項；使用者仍自行完成每一次抽選。

### 2.3 後續可選

- LINE Messaging API 通知（使用本專案自己的 LINE Official Account，不是讀取各 Funbox 官方帳號的私訊或廣播內容）。
- 其他縣市與其他零售通路。
- 歷史價格、庫存變化與各門市公告時間軸。

### 2.4 明確不做

- 不保存誠品帳號密碼、LINE 密碼、登入 Cookie 或驗證碼。
- 不代替使用者登入誠品或 LINE。
- 不自動按下 Funbox 抽選頁的「參加抽選」、不自動送出個資、不自動結帳或付款。
- 不繞過 CAPTCHA、排隊頁、限購、身分驗證或網站存取限制。
- 不宣稱第三方目錄中的舊活動仍可參加；已過期連結只能顯示為歷史紀錄。

## 3. 主要使用流程

### 3.1 初次設定

1. 使用者開啟搶購助手，預設地區為「台中市」。
2. 選擇想追蹤的 Funbox 門市與陀螺型號（例如 BX-53、UX-17、CX-13）。
3. 使用者可逐店開啟 LINE 好友連結並自行加入官方帳號。
4. 使用者可自行登入誠品及 LINE；本網站只提供外部連結，不讀取或管理登入資訊。
5. 可將網站加入手機主畫面；抽選時建議在同一支手機使用熟悉的 LINE／瀏覽器環境開啟官方連結。

### 3.2 Funbox 抽選／販售

1. 系統列出已核實的新公告，依截止時間排序。
2. 顯示門市、商品、活動方式、時間、限購（有明確公告才顯示）、公告來源及抽選連結。
3. 使用者點「開啟官方抽選頁」。
4. 使用者在 Funbox 指定頁面自行確認資格、條款及資料，並親自按下參加抽選。
5. 返回助手後，系統可偵測頁面重新取得焦點，提示「是否已完成？」；不得直接將其記成抽選成功。
6. 使用者手動選擇「已完成」、「尚未完成」或「稍後處理」。

**重要：**瀏覽器只能可靠地記錄「已開啟／已返回」等前端事件，無法僅靠返回事件證明官方抽選成功。成功狀態必須由使用者確認，或在未來有官方可驗證回執時才更新。

### 3.3 誠品購買

1. 使用者建立想追蹤的商品清單。
2. 系統檢查誠品公開商品頁的價格與可見販售訊息。
3. 發生缺貨／可購買訊息變化或價格變化時，建立變更紀錄並通知。
4. 使用者點「前往誠品」，在誠品官方網站自行登入、確認庫存、加入購物車及結帳。

「加入購物車」或商品頁顯示可購買，不保證結帳時仍有庫存；實際是否成立以誠品結帳結果及訂單確認為準。

## 4. 網頁資訊架構

### 4.1 導覽分頁

- **總覽**：近期新公告、即將截止、追蹤商品變化、資料更新時間。
- **Funbox 門市**：依縣市與門市篩選；逐店顯示 LINE、公告來源及地址。
- **抽選／販售活動**：商品與門市活動清單；可切換「全部／進行中／尚未開始／已截止／待確認」。
- **誠品商品**：追蹤清單、價格、頁面販售訊息及商品連結。
- **我的清單**：收藏商品、關注門市、已處理紀錄。
- **設定**：預設縣市、通知方式、抽選操作模式。

### 4.2 首頁摘要

- 只顯示實際有資料支持的數字，例如「追蹤中的商品」、「待處理活動」及「本日新變化」。
- 不得把未知庫存顯示為有貨，也不得把沒有新公告顯示為缺貨。
- 明確區分「沒有查到新公告」與「已確認沒有庫存」。

### 4.3 商品與活動卡片欄位

**Funbox 活動卡片**

- 商品型號、中文商品名稱
- 門市名稱、縣市
- 活動方式：LINE 抽選／現場販售／預購／其他／待確認
- 活動狀態：尚未開始／進行中／已截止／取消／待確認
- 開始、截止時間（含台灣時區）
- 價格、限購規則（僅在來源明確提供時）
- Facebook 原始公告、官方 LINE、抽選頁連結
- 公告發布時間、資料擷取時間、最後人工核對時間

**誠品商品卡片**

- 型號、商品名稱、商品圖片（來源允許且圖片穩定時）
- 目前頁面價格
- 頁面販售訊息：可見加入購物車／顯示缺貨／預購／未知
- 商品頁連結
- 最近一次檢查時間、最近一次狀態變更時間

## 5. 資料來源與可信度

來源優先順序：

1. 誠品官方商品頁、Funbox 官方網站／官方購物網站。
2. 各門市官方 Facebook 公告、可確認身份的官方 LINE 帳號及其活動連結。
3. 使用者維護的 Google Sheet：門市主名單、Facebook URL、LINE ID。
4. UXUX11：補充 LINE 門市名錄及抽選批次探索來源；其頁面未公開可核實的資料擷取方法。
5. BeyBuilder：商品型號／中文品名、門市活動歷史與舊抽選批次探索來源；其舊活動可能已過期。
6. 玩家轉貼／社群截圖：僅作線索，需回到原始公告核對。

每筆資料必須保留來源網址。若沒有可驗證來源，狀態標為「待確認」，不可自行補造連結、價格、庫存或活動時間。

## 6. 地區與門市資料設計（支援未來擴充）

### 6.1 地區設計原則

採用「縣市 → 門市」兩層資料，不把台中市寫死在程式中。每家門市有穩定 `storeId`，例如 `tw-txg-funbox-zhongyou`。未來新增台北、高雄，只需新增地區與門市資料，篩選器自動讀取，不需修改主要 UI 邏輯。

建議分享網址：

```text
/?region=TW-TXG&store=all&q=BX-53&tab=draw
/?region=TW-TXG&store=tw-txg-funbox-zhongyou&q=UX-17&tab=draw
/?region=TW-TPE&store=all&q=CX-13&tab=draw
```

可兼容參考 BeyBuilder 的 `c`、`s`、`q` 參數概念，但本專案應使用穩定 ID，避免門市改名造成網址失效。

## 6.4 多來源合併與資料來源追蹤

採用兩套主資料，不將所有資訊混成同一張清單：

- **門市聯絡資料（store directory）**：Google Sheet 的 68 筆資料是主要來源；UXUX11 LINE 名錄中未出現在 Google Sheet 的 10 個地點存於 `stores-supplemental.json`。每次 Google Sheet 同步後都會重新合併，避免補充資料被覆蓋。若同一 LINE ID 對應兩個實體地點，保留兩筆地點並標記共用帳號。
- **抽選／販售活動（draw events）**：獨立存放於 `draw-events.json`。UXUX11 當期活動頁與 BeyBuilder 歷史目錄先作為外部探索來源，記錄於 `draw-sources.json`。在每筆活動的官方抽選網址、商品、起訖時間可核實前，不把它們自動標記為有效活動。

每一筆導入資料應保留來源名稱、來源網址、觀察／擷取時間、公告時間、活動時間、是否推估時間及核實狀態。不得因某店未出現在當期活動名單，就推論該店無庫存或沒有販售。

**第三方取得方法的限制：** UXUX11 與 BeyBuilder 的公開頁面提供整理後的清單與批次更新時間，但未找到能核實其後台爬蟲、API 或人工編輯流程的公開技術說明。因此本專案只引用它們可觀察的公開資料結構，不宣稱已掌握作者的內部實作。詳見 `source-research.md`。

### 7.5 狀態定義

- 活動 `status`：`announced`、`upcoming`、`open`、`closed`、`cancelled`、`needs-verification`。
- 販售 `method`：`line-draw`、`in-store`、`online`、`preorder`、`other`、`unknown`。
- 商品頁販售訊息：`add-to-cart-visible`、`sold-out-visible`、`preorder-visible`、`not-listed`、`unknown`。
- 使用者進度：`not-started`、`opened`、`user-confirmed-complete`、`skipped`。
- 資料可信度：`official`、`third-party-discovery`、`user-submitted`、`needs-manual-check`。

所有時間以 ISO 8601 儲存，並使用 `Asia/Taipei` 顯示。每個時間欄位需明確區分公告時間、活動時間、資料擷取時間與人工核對時間。

## 8. 監控與通知設計

### 8.1 誠品

- 從公開商品頁檢查標題、型號、價格及可見的購物操作訊息。
- 僅在頁面結構穩定且允許自動存取時擷取；若遇到驗證、封鎖、動態載入失敗或頁面改版，狀態改為 `unknown`，不可沿用舊有貨狀態冒充即時資料。
- 第一版建議 15–30 分鐘檢查一次作為起始設定；依網站負載、使用規範及技術穩定度再調整。排程工作可能延遲，不能承諾秒級即時。
- 保留狀態快照，偵測「未知／缺貨 → 可見加入購物車」等變化。

### 8.2 Funbox

- 官方官網／官方購物網站門市資料可作為門市名錄來源。
- 公開 Facebook 公告若可穩定、合規取得，才納入自動檢查。
- 各門市 LINE 好友連結只用於讓使用者加入／開啟官方帳號；不代表可以讀取其他官方帳號對使用者推送的私人訊息或聊天內容。
- 無法取得的公告，支援使用者貼上 Facebook 公告網址、抽選網址、截圖或文字後人工建立活動。
- 第三方抽選資料可匯入歷史資料，但必須保留 `sourceType=third-party` 及原始時間，不可自動標成目前進行中。

### 8.3 通知

- MVP：頁面開啟期間的前景提醒；可搭配瀏覽器通知權限。
- PWA 背景推播需要 Push Service、Service Worker 及可用的後端／Serverless endpoint；僅有 GitHub Pages 靜態網站並不足以自行發送背景推播。
- LINE 通知可使用本專案自己的 LINE Official Account + Messaging API。LINE Notify 已於 2025-03-31 結束服務；不要採用舊 LINE Notify Token。
- LINE Messaging API 的 webhook 是接收使用者加入／傳訊給**本專案自己的官方帳號**等事件，不是讀取 Funbox 官方帳號向使用者發送的訊息。

## 9. 技術架構建議

### 9.1 前端

- HTML、CSS、JavaScript（第一版優先選輕量方案，不先引入大型框架）。
- Mobile-first 響應式版面。
- PWA：manifest、service worker、加入主畫面；離線時顯示最後成功載入的資料與資料時間。
- `localStorage` 保存使用者收藏、篩選條件與抽選處理進度；不保存帳號密碼或登入憑證。

## 10. 介面與操作細節

- 預設開啟台中市，並提供「全部台中門市」與個別門市篩選。
- 商品代碼搜尋支援大小寫不敏感、中文名稱、別名。
- 「即將截止」按活動截止時間升冪排序。
- 已截止活動預設收合，但可切換顯示歷史紀錄。
- 抽選佇列至少提供「手動逐項」與「快速連續處理」兩種模式；快速模式仍需使用者逐一開啟及親自完成官方操作。
- 每張活動卡片的主要按鈕標示清楚：`開啟官方抽選頁`、`查看公告`、`加入門市 LINE`；不能用模糊的「抽獎成功」字樣。
- 抽選頁開啟後，返回助手只彈出確認提示，不自動判定成功。
- 不要把「加入 LINE 好友」和「抽選成功」混為一談。

## 11. 資料驗證與失效處理

- 門市資料需有來源 URL、最後核對時間、核對狀態。
- 外部連結定期檢查 HTTP 狀態；LINE scheme 或 App deep link 不可只用一般 HTTP 200 判斷好友帳號有效。
- 抽選活動若截止時間已過，前端自動標示已截止；但若來源時間缺漏，標示待確認，不猜測。
- 同一門市同一商品、同一公告網址需去重。
- 變更門市名稱時保留 `storeId`，以 aliases 維持舊 URL 與歷史紀錄。
- 抽選活動資料有衝突時優先顯示官方原始公告，並標示衝突，不自行選一個時間。
- 抓取失敗時顯示最後成功時間及「目前無法確認」，不要沿用舊狀態偽裝最新。

## 12. 驗收標準

### MVP 驗收

- [ ] 手機瀏覽器可正常使用，常用操作不需橫向捲動。
- [ ] 預設地區為台中市。
- [ ] 可篩選台中全部門市與單一門市。
- [ ] 可用 BX／UX／CX 型號與中文名稱搜尋。
- [ ] 每家門市可查看地址、LINE 入口及來源資訊；未驗證欄位需標示待確認。
- [ ] 每筆抽選／販售活動可顯示時間、狀態及原始來源連結。
- [ ] 使用者可標記已開啟及已確認完成，重整頁面後進度仍保留。
- [ ] 誠品商品頁可以直接開啟，商品頁價格／販售狀態附最後檢查時間。

- [ ] 分享網址可保留縣市、門市、商品搜尋條件。
- [ ] 新增一個縣市與一筆門市 JSON 後，選單會自動出現該縣市，不需修改程式邏輯。

### 監控階段驗收

- [ ] 抓取失敗時回報未知狀態，而不是誤報有貨／缺貨。
- [ ] 可記錄狀態變化及來源時間。
- [ ] 只在符合通知條件時推播，並避免同一事件重複通知。
- [ ] 背景通知服務金鑰不會出現在前端 repository。

## 13. 建議開發里程碑

1. **M0 資料校正**：確認台中 11 個 LINE 候選帳號、官方門市地址、各店 Facebook 頁及目前販售模式。
2. **M1 靜態 MVP**：建立手機版頁面、台中門市、搜尋篩選、活動卡片、LINE／公告／抽選外連及手動進度。
3. **M2 誠品監控**：加入商品清單、公開商品頁檢查、價格與頁面販售訊息快照。
4. **M3 Funbox 公告管理**：加入公告貼上／匯入、來源核對及活動時間狀態管理；可自動擷取的公開來源再逐一整合。
5. **M4 通知與 PWA**：前景通知先行，再評估 Web Push 或 LINE Messaging API。
6. **M5 地區擴充**：使用同一資料模型新增其他縣市，不修改核心 UI。
